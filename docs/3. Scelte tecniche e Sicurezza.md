# Architettura:
---
>**Scelta di Blazor Server**
>Il presente documento illustra le motivazioni tecniche e di sicurezza alla base della scelta di adottare **Blazor Server** in .NET 9 per lo sviluppo della piattaforma intranet aziendale **PostIn**, preferendolo ad architetture basate su Blazor WebAssembly o Single Page Application (SPA) tradizionali con API REST.
---
## Scelta di Blazor Server

**Ambiente intranet e risorse client**
In un contesto aziendale la rete locale (LAN/WLAN) offre banda elevata e latenza trascurabile. I dispositivi in uso ai dipendenti possono tuttavia essere macchine con risorse limitate o datate.

Con **Blazor Server**:
- L'intera elaborazione C#, il rendering e le query al database avvengono sul server.
- Il client scarica solo un piccolo script JavaScript per la connessione **SignalR (WebSocket)** e riceve esclusivamente le differenze di DOM da renderizzare.
- Si evitano i lunghi tempi di caricamento iniziale (*cold start*) del runtime .NET in WebAssembly.

**Sicurezza architetturale nessuna API esposta**
In un'applicazione essendo esposta su una rete ha una superfice di attacco più ampia.
Con Blazor Server:
- **Non vengono esposte endpoint** al client per il recupero dei dati.
- Tutta la logica di business e le query al database rimangono confinate all'interno del processo server.
- Il browser riceve esclusivamente aggiornamenti dell'interfaccia utente (HTML diff via SignalR).

## Autenticazione e Reindirizzamento al Login

PostIn usa l'autenticazione basata su **cookie di sessione** (`CookieAuthenticationDefaults`), configurata in `Program.cs`.

```csharp
options.LoginPath   = "/login";
options.LogoutPath  = "/logout";
options.AccessDeniedPath = "/AccessDenied";
```

Ogni pagina che richiede autenticazione è decorata con `@attribute [Authorize]`. Se un utente anonimo tenta di raggiungere qualsiasi URL protetto, il middleware di autenticazione lo reindirizza automaticamente a `/login` **prima** che il componente Blazor venga eseguito. L'utente non può mai accedere a dati o funzionalità senza aver eseguito il login.

## Protezione delle Immagini di Copertina

Le immagini caricate dai dipendenti non vengono servite come file statici pubblici. In `Program.cs` è definito un **endpoint HTTP dedicato e protetto**:
- **Path traversal bloccato**: `Path.GetFileName()` elimina qualsiasi tentativo di risalire la struttura di directory (es. `../../etc/passwd`).
- **Accesso riservato agli autenticati**: la direttiva `.RequireAuthorization()` respinge le richieste anonime prima ancora che il codice di lettura file venga eseguito. Le immagini non sono raggiungibili da fuori la piattaforma.

---
## Hashing Sicuro delle Password

Le password non vengono mai salvate in chiaro. La classe `PasswordHelper` usa l'**`ASP.NET Core Identity PasswordHasher`**, che applica l'algoritmo **PBKDF2 con salt casuale** per ogni password:
- Il **salt è generato automaticamente** e incorporato nell'hash due hash della stessa password sono sempre diversi.
- La verifica gestisce esplicitamente il caso di **hash o password vuoti**, restituendo `false` senza lanciare eccezioni.
- In fase di login, il messaggio di errore è volutamente **generico** ("Username o password non corretti") per non rivelare se l'account esiste o meno.

## Controllo degli Accessi per Ruolo

PostIn definisce due ruoli: **Admin** (valore `1`) e **User** (valore `0`), memorizzati nel database e inclusi nel cookie come `ClaimTypes.Role` al momento del login.

Le pagine di amministrazione sono protette dall'attributo:

```csharp
@attribute [Authorize(Roles = "Admin")]
```

Blazor verifica il ruolo prima di renderizzare il componente: un utente standard che tenta di raggiungere `/admin/*` viene bloccato automaticamente dal middleware.

### Perché solo l'Admin può creare account?

PostIn è una **intranet aziendale chiusa**: non è prevista la registrazione autonoma. Solo un amministratore conosce l'organico aziendale e può creare account per i dipendenti. Questo impedisce che chiunque possa registrarsi e accedere a contenuti riservati. L'Admin, tramite la pagina `/admin/users`, crea l'account con una password iniziale che l'utente dovrà poi cambiare (da implementare un sistema migliore).

In aggiunta, `AdminUsers.razor` blocca via codice anche la possibilità che un Admin modifichi o disabiliti il **proprio account**:

```csharp
Disabled="@(isActionLoading || isCurrentUser)"
Title="Non puoi modificare il tuo stesso ruolo"
```

Questo evita che un errore amministrativo lasci la piattaforma senza alcun Admin attivo.

## Vincoli di Integrità a Livello Database

La sicurezza non si applica solo al livello applicativo. Il database stesso include vincoli strutturali configurati via Entity Framework Core:

- **UNIQUE su `Username`**: impedisce la creazione di account con lo stesso username, anche se la richiesta bypassasse il controllo applicativo.
- **UNIQUE su `NomeCategoria`**: nessuna categoria duplicata può esistere nel DB.
- **CHECK CONSTRAINT `CK_IscrizioniFollow_NoSelfFollow`**: una riga con `FK_Follower = FK_Followed` è rifiutata direttamente dal database, indipendentemente da qualsiasi controllo nel codice.
- **`OnDelete: Restrict`** sull'autore degli articoli: un account non può essere eliminato finché ha post pubblicati, preservando la coerenza dei dati.
- **`OnDelete: Cascade`** su tutte le entità figlio (commenti, like, salvataggi, visualizzazioni): l'eliminazione di un articolo rimuove automaticamente tutti i dati correlati senza lasciare record orfani.
